# X.509 Certificates & Anatomy

> [!abstract] The 30-Second Summary
> An **X.509 certificate** ([RFC 5280](https://datatracker.ietf.org/doc/html/rfc5280)) is a standardized digital passport that cryptographically binds an identity (domain name, IP, organization) to a public key. Defined in **ASN.1**, serialized into binary **DER**, and encoded as base64 **PEM** (`-----BEGIN CERTIFICATE-----`), its behavior is dictated by **v3 Extensions**: `basicConstraints` (CA vs. Leaf), `keyUsage` / `extendedKeyUsage` (permitted cryptographic tasks), and `subjectAltName` (SAN). Today, the legacy **Common Name (CN)** is deprecated; modern host validation relies **exclusively on SAN**.

---

## 1 · Formats, Schemas & File Encodings

```
ASN.1 Schema (Abstract Syntax Notation One)
   │
   ▼ Serialized according to
DER (Distinguished Encoding Rules) ──► Raw binary bytes (.der, .cer)
   │
   ▼ Encoded with Base64 & ASCII Headers
PEM (Privacy Enhanced Mail) ─────────► Text files (.pem, .crt, .key)
```

| Format / Container | File Extension | Characteristics & Real-World Analogy |
|---|---|---|
| **PEM** (*Privacy Enhanced Mail*) | `.pem`, `.crt`, `.cer`, `.key` | **ASCII Text**. Base64-encoded DER wrapped between headers (`-----BEGIN CERTIFICATE-----`). De facto standard on Linux, Nginx, Apache. *Analogy: A printed PDF copy of your passport you can read on screen.* |
| **DER** (*Distinguished Encoding Rules*) | `.der`, `.cer` | **Binary**. Direct binary encoding of the ASN.1 structure. Common in Java keytool, Windows, and microcontrollers. *Analogy: The raw barcode on the back of your driver's license.* |
| **PKCS#12 / PFX** | `.p12`, `.pfx` | **Encrypted Binary Container**. Bundles certificate, intermediate chain, and **private key** into a password-protected archive. Used in Windows IIS and macOS Keychain. *Analogy: A locked ziplock bag holding your passport, visa, and house key.* |
| **PKCS#7 / P7B** | `.p7b`, `.p7c` | **Signed Container**. Contains certificates and CRLs, but **never private keys**. Used for exporting certificate chains in Windows. |

### Quick Jargon Decoder

| Cryptographic Term | What It Actually Means | Real-World Metaphor |
|---|---|---|
| **X.509** | The official global standard format for digital identity cards. | Standard physical passport layout (photo left, name top, expiry bottom). |
| **SAN** (*Subject Alternative Name*) | The official list of all domain names and IPs this certificate protects. | The list of names authorized on a family amusement park pass. |
| **CN** (*Common Name*) | The legacy, retired single-hostname field. | An old handwritten paper ID card that has been superseded by digital cards. |

## 2 · Anatomy of an X.509 Version 3 Certificate

Standardized in [RFC 5280](https://datatracker.ietf.org/doc/html/rfc5280), an X.509 v3 certificate consists of three primary blocks:
1. **TBSCertificate** (*To-Be-Signed Certificate*): The payload containing identity, public key, validity, and extensions.
2. **SignatureAlgorithm**: The algorithm used by the CA to sign the TBSCertificate (e.g. `sha256WithRSAEncryption` or `ecdsa-with-SHA384`).
3. **SignatureValue**: The cryptographic signature produced by the issuing CA's private key.

```
Certificate
├── TBSCertificate ("To-Be-Signed" Payload)
│   ├── Version: v3 (0x2)
│   ├── Serial Number: Unique positive integer (up to 20 octets, RFC 5280 §4.1.2.2)
│   ├── Signature: AlgorithmIdentifier (e.g., sha256WithRSAEncryption)
│   ├── Issuer: Distinguished Name (DN) of the Issuing CA
│   ├── Validity:
│   │   ├── Not Before: 2026-09-21 00:00:00 UTC
│   │   └── Not After:  2027-10-23 00:00:00 UTC
│   ├── Subject: Distinguished Name (DN) of the Certificate Holder
│   ├── Subject Public Key Info:
│   │   ├── Algorithm: rsaEncryption or id-ecPublicKey
│   │   └── Public Key Bits: The raw public key data (e.g. 2048-bit RSA)
│   └── Extensions (v3 only):
│       ├── basicConstraints (Critical: CA:FALSE)
│       ├── keyUsage (Critical: digitalSignature, keyEncipherment)
│       ├── extendedKeyUsage (serverAuth)
│       ├── subjectAltName (DNS:labapp.com, IP:192.168.100.20)
│       ├── subjectKeyIdentifier (SKI)
│       └── authorityKeyIdentifier (AKI)
├── SignatureAlgorithm: sha256WithRSAEncryption
└── SignatureValue: 92:b4:3a:a0:26:... (Cryptographic signature from Issuing CA)
```

## 3 · How the Certificate is Used: The 3 Browser Checks

During the TLS Handshake ([RFC 8446](https://datatracker.ietf.org/doc/html/rfc8446)), when the server sends its certificate, the browser executes three instant local checks before encrypting traffic:

```
[ Visitor Browser ]                                             [ Nginx Web Server ]
         │                                                               │
         │ ─── 1. "ClientHello: I want a secure TLS connection" ───────► │
         │                                                               │
         │ ◄── 2. "ServerHello: Here is my X.509 Certificate Chain!" ──── │
         │                                                               │
         ├───────────────────────────────────────────────────────────────┤
         │ BROWSER RUNS 3 OFFLINE LOCAL CHECKS:                          │
         │ A. Identity Check: Does URL typed match an entry in SAN?     │
         │ B. Expiration Check: Is current time between NotBefore/After? │
         │ C. Signature Check: Does CA signature math match Root Store?  │
         ├───────────────────────────────────────────────────────────────┤
         │                                                               │
         │ ─── 3. "Checks pass! Let's negotiate session keys." ────────► │
         │ ◄===========================================================► │
         │            Encrypted HTTPS Session Flowing (Padlock ON)       │
```

### Proving Ownership: Why an Attacker Cannot Just Steal Your Cert

An X.509 certificate is a **public document**. Anyone can download `labapp.crt` over the network. Why can't an attacker (Eve) steal your certificate and use it to impersonate your website?

> [!important] Proof of Private Key Possession
> During the TLS handshake, the browser requires the server to perform an active cryptographic operation using the **Server Private Key** (such as signing the ephemeral Diffie-Hellman handshake parameters in TLS 1.3).
> - If Eve presents your public certificate, she does **not** have your `labapp.key` private key.
> - She cannot produce a valid handshake signature.
> - The browser detects the mathematical mismatch with the public key inside the certificate and aborts the connection with a fatal TLS alert.

## 4 · Critical vs. Non-Critical Extensions (RFC 5280 §4.2)

Every v3 extension includes a boolean flag: `critical = TRUE` or `critical = FALSE` (default).

> [!danger] The RFC 5280 Criticality Rule
> *"A certificate-using system MUST reject the certificate if it encounters a critical extension it does not recognize or cannot process."*

### Key Extensions Breakdown

| Extension | Target Entity | Recommended Setting | Production Purpose |
|---|---|---|---|
| **`basicConstraints`** | CA / Leaf | `critical, CA:TRUE` (CA)<br>`critical, CA:FALSE` (Leaf) | **The fundamental boundary**. Prevents a compromised web server from issuing rogue certificates for other domains. |
| **`keyUsage`** | All | `critical, digitalSignature, keyEncipherment` (TLS 1.2)<br>`critical, keyCertSign, cRLSign` (CA) | Restricts cryptographic operations. TLS 1.3 exclusively requires `digitalSignature` for ephemeral ECDHE key authentication. |
| **`extendedKeyUsage`** | Leaf | `serverAuth` (Web Server)<br>`clientAuth` (mTLS) | Explicitly specifies protocol roles ([RFC 5280 §4.2.1.12](https://datatracker.ietf.org/doc/html/rfc5280#section-4.2.1.12)). |
| **`subjectAltName`** | Leaf | `DNS:..., IP:...` | Mandatory domain/IP identifier list ([RFC 6125](https://datatracker.ietf.org/doc/html/rfc6125)). |
| **`subjectKeyIdentifier` (SKI)** | All | `hash` (SHA-1 of public key) | Digital barcode identifying this certificate's public key. |
| **`authorityKeyIdentifier` (AKI)** | Child Certs | `keyid,issuer:always` | Points directly to the SKI of the parent CA that signed this certificate. |

## 5 · The Death of Common Name (CN) and the Supremacy of SAN

Historically, a web server's hostname was placed in the Subject's **Common Name (CN)** attribute: `CN = labapp.com`.

### Why Common Name is Deprecated
1. **Ambiguity**: `CN` was originally designed in the X.500 directory standard for human names (e.g. "John Doe"), not DNS domain names or IP addresses.
2. **Single Identity Limit**: A certificate could only have one primary `CN`, failing multi-domain, sub-domain, and dual-stack IPv4/IPv6 architectures.
3. **No IP/DNS Type Distinction**: A parser cannot determine whether `"192.168.100.20"` in a CN is an IP address or a string literal domain.

### Formal Deprecation Timeline & Modern 2026 Standards
- **[RFC 2818](https://datatracker.ietf.org/doc/html/rfc2818)** (May 2000): Established that if a `subjectAltName` is present, it MUST be used; `commonName` is considered fallback.
- **[RFC 6125](https://datatracker.ietf.org/doc/html/rfc6125)** (March 2011): Formally deprecated `commonName` across all transport protocols.
- **[CA/Browser Forum Baseline Requirements §7.1.4.2.2 & §7.1.4.3.1](https://cabforum.org/working-groups/server-certificate/baseline-requirements/)**:
  - `subjectAltName` is **MANDATORY**.
  - *"CAs SHOULD NOT include a commonName attribute in the Subject of Certificates issued to Domain Names."* If included, it MUST be an exact copy of one of the SAN dNSName entries.
- **Modern Browsers (Chrome 58+, Firefox, Safari, curl)**: **Removed the fallback completely**. Browsers validate TLS identity **solely against `subjectAltName`**. If SAN is missing, the connection fails with `ERR_CERT_COMMON_NAME_INVALID`, even if `CN` is 100% correct.
- **State of the Art (September 2026)**: Major automated CAs (Let's Encrypt, Google Trust Services, Cloudflare) actively issue TLS certificates with **no `commonName` attribute in the Subject at all** (`Subject: C = PH, O = AirNav DAS Lab`).

### The Modern SAN Syntax

```ini
subjectAltName = @alt_names

[alt_names]
DNS.1 = labapp.com         # Primary domain
DNS.2 = *.labapp.com       # Wildcard domain
IP.1  = 192.168.100.20     # Direct IP access
IP.2  = 10.10.10.10        # Internal interface
```

## 6 · Inspecting Certificates with OpenSSL

```bash
# Inspect a local certificate file:
openssl x509 -in cert.pem -text -noout

# Inspect live certificate presented by a remote server over TLS:
openssl s_client -connect 192.168.100.20:443 -servername labapp.com </dev/null | openssl x509 -text -noout
```

### Essential Verification Checklist:
- [x] **Validity**: Is current time between `Not Before` and `Not After`?
- [x] **Basic Constraints**: Does it state `CA:FALSE` for web servers?
- [x] **Subject Alternative Name**: Are requested domains/IPs listed under `DNS:` or `IP Address:`?
- [x] **Extended Key Usage**: Does it include `TLS Web Server Authentication` (`serverAuth`)?
