# X.509 Certificates & Anatomy

> [!abstract] The 30-second version
> An **X.509 certificate** (standardized in **RFC 5280**) is a structured cryptographic passport that binds an identity (domain, IP, organization) to a public key. The certificate is formally defined in **ASN.1**, serialized into binary **DER**, and commonly stored as base64-armored **PEM** (`-----BEGIN CERTIFICATE-----`). Its behavior is governed by **v3 Extensions**: `basicConstraints` dictates whether the certificate can sign other certificates, `keyUsage` and `extendedKeyUsage` specify permitted cryptographic operations, and `subjectAltName` (SAN) defines the exact valid domain names and IP addresses. Today, the legacy **Common Name (CN)** is deprecated by all modern browsers; host validation relies **exclusively on SAN**.

---

## 1 · Formats, Schemas & File Encodings

It is common to confuse file extensions (`.crt`, `.pem`, `.key`, `.der`) with actual encoding formats. In cryptography, format and encoding have precise technical definitions:

```
ASN.1 Schema (Abstract Syntax Notation One)
   │
   ▼ Serialized according to
DER (Distinguished Encoding Rules) ──► Raw binary bytes (.der, .cer)
   │
   ▼ Encoded with Base64 & ASCII Headers
PEM (Privacy Enhanced Mail) ─────────► Text files (.pem, .crt, .key)
```

| Format / Container | File Extension | Characteristics & Use Cases |
|---|---|---|
| **PEM** (*Privacy Enhanced Mail*) | `.pem`, `.crt`, `.cer`, `.key` | **ASCII Text**. Base64-encoded DER representation wrapped between headers: `-----BEGIN CERTIFICATE-----` and `-----END CERTIFICATE-----`. De facto standard on Linux, Nginx, Apache, OpenSSL. |
| **DER** (*Distinguished Encoding Rules*) | `.der`, `.cer` | **Binary**. The direct binary encoding of the ASN.1 structure. Common in Java keytools, Windows platforms, and embedded systems. |
| **PKCS#12 / PFX** | `.p12`, `.pfx` | **Encrypted Binary Container**. Bundles the certificate, entire intermediate chain, and the **private key** into a single password-protected file. Standard in Windows IIS, macOS Keychain, and Java. |
| **PKCS#7 / P7B** | `.p7b`, `.p7c` | **Signed Container**. Contains certificates and CRLs, but **never contains private keys**. Used for exporting certificate chains in Windows environments. |

## 2 · Anatomy of an X.509 Version 3 Certificate

Standardized by the ITU-T and refined for the Internet in **RFC 5280**, an X.509 v3 certificate consists of three primary blocks:
1. **TBSCertificate** (*To-Be-Signed Certificate*): The payload containing identity, public key, validity, and extensions.
2. **SignatureAlgorithm**: The algorithm identifier used by the CA to sign the TBSCertificate (e.g. `sha256WithRSAEncryption` or `ecdsa-with-SHA384`).
3. **SignatureValue**: The actual bit-string cryptographic signature produced by the issuing CA's private key.

```
Certificate
├── TBSCertificate
│   ├── Version: v3 (0x2)
│   ├── Serial Number: Unique positive integer (up to 20 octets)
│   ├── Signature: AlgorithmIdentifier (e.g., ecdsa-with-SHA384)
│   ├── Issuer: Distinguished Name (DN) of the Issuing CA
│   ├── Validity:
│   │   ├── Not Before: 2026-09-21 00:00:00 UTC
│   │   └── Not After:  2027-09-21 23:59:59 UTC
│   ├── Subject: Distinguished Name (DN) of the Certificate Holder
│   ├── Subject Public Key Info:
│   │   ├── Algorithm: id-ecPublicKey or rsaEncryption
│   │   └── Public Key Bits: The raw public key data
│   └── Extensions (v3 only):
│       ├── basicConstraints (Critical)
│       ├── keyUsage (Critical)
│       ├── extendedKeyUsage
│       ├── subjectAltName (SAN)
│       ├── subjectKeyIdentifier (SKI)
│       └── authorityKeyIdentifier (AKI)
├── SignatureAlgorithm: ecdsa-with-SHA384
└── SignatureValue: 7a:4f:9b:1c:... (Cryptographic signature from CA)
```

## 3 · Critical vs. Non-Critical Extensions (RFC 5280 §4.2)

Every v3 extension includes a boolean flag: `critical = TRUE` or `critical = FALSE` (default).

> [!danger] The RFC 5280 Criticality Rule
> *"A certificate-using system MUST reject the certificate if it encounters a critical extension it does not recognize or cannot process."*
> If an extension is non-critical, an application that does not understand the extension may safely ignore it and continue processing.

### Key Extensions Deep-Dive

#### 1. `basicConstraints` (MUST be Critical for CAs)
Distinguishes whether the certificate belongs to a **Certificate Authority** or an **End-Entity (leaf)**.
- **For Root & Intermediate CAs**: `CA:TRUE`. Optionally sets `pathlen`:
  - `pathlen:0` means this CA can issue end-entity certificates, but **cannot issue subordinate CA certificates**.
- **For Web Servers (Nginx)**: `CA:FALSE`.
> [!caution] Security Impact
> If `basicConstraints` is missing or accidentally set to `CA:TRUE` on a web server certificate, that web server could theoretically issue valid SSL certificates for `google.com` or `bank.com`, and clients trusting the parent CA would accept them!

#### 2. `keyUsage` (Typically Critical)
Restricts the fundamental cryptographic operations the public key may perform:
- `digitalSignature`: Verifying digital signatures (used in TLS ephemeral handshakes, DHE/ECDHE).
- `keyEncipherment`: Encrypting symmetric keys directly (used in legacy static RSA key exchange; disabled in TLS 1.3).
- `keyCertSign`: Verifying signatures on other public key certificates (**exclusive to CAs**).
- `cRLSign`: Verifying revocation lists (CRLs).

#### 3. `extendedKeyUsage` (EKU)
Defines specific high-level application protocols allowed to use the key:
- `serverAuth`: TLS Web Server Authentication (Nginx, Apache).
- `clientAuth`: TLS Web Client Authentication (Mutual TLS / mTLS).
- `codeSigning`: Executable code signing.
- `emailProtection`: S/MIME email encryption and signing.

#### 4. `subjectKeyIdentifier` (SKI) & `authorityKeyIdentifier` (AKI)
- **SKI**: A 160-bit SHA-1 hash of the certificate's own public key.
- **AKI**: The SKI of the issuing CA that signed this certificate.
- **Purpose**: Enables the client's path-validation engine to rapidly match child certificates to their parent issuer without parsing complex Distinguished Names.

## 4 · The Death of Common Name (CN) and the Supremacy of SAN

Historically, a web server's hostname was placed in the Subject's **Common Name (CN)** attribute:
`Subject: CN=192.168.100.20, O=Lab, C=PH`

### Why Common Name is Deprecated

1. **Ambiguity**: The `CN` field was originally intended in the X.500 directory standard for a human person's name (e.g., "John Doe"), not a Fully Qualified Domain Name (FQDN) or IP address.
2. **Single Identity Limit**: A certificate can only have one primary `CN`. Modern multi-domain environments and dual IPv4/IPv6 architectures require multiple names.
3. **No Distinction between IP and Domain**: A CN string cannot explicitly declare whether `"192.168.100.20"` is a DNS hostname or a raw IP address.

### Formal Deprecation Timeline & Modern 2026 Status
- **RFC 2818 (HTTP Over TLS, May 2000)**: §3.1 explicitly specified: *"If a subjectAltName extension of type dNSName is present, that MUST be used as the identity. Otherwise, the (deprecated) commonName field is used."*
- **RFC 6125 (March 2011)**: Formally deprecated the fallback to `commonName` across all application protocols.
- **CA/Browser Forum Baseline Requirements (§7.1.4.2.2 & §7.1.4.3.1)**:
  - **SAN is Mandatory**: The `subjectAltName` extension MUST contain all domain names and IP addresses.
  - **CN Deprecated**: *"CAs SHOULD NOT include a commonName attribute in the Subject of Certificates issued to Domain Names."* If present, it MUST contain a single entry that exactly matches one of the SAN dNSName entries.
- **Chrome 58+ (2017) & Modern Browsers**: **Removed the fallback completely**. If the requested hostname or IP is not explicitly listed in the `subjectAltName` extension, Chrome, Edge, Safari, and curl immediately reject the connection with `ERR_CERT_COMMON_NAME_INVALID` or `SSL: no alternative certificate subject name matches target host name`, even if the Common Name is present and correct!
- **State of the Art (September 2026)**: Leading public Certificate Authorities (e.g., Let's Encrypt, Google Trust Services) actively issue TLS certificates with **no `commonName` attribute in the Subject at all** (e.g. `Subject: C=US, O=Organization` or completely empty Subjects for Domain Validated certs per RFC 5280 §4.1.2.6). All identity assertions reside exclusively within `subjectAltName`.

### The Solution: Subject Alternative Name (SAN)
SAN (`subjectAltName`) allows an explicit, typed list of valid identities:
```ini
subjectAltName = @alt_names

[alt_names]
DNS.1 = labapp.com
DNS.2 = *.labapp.com
DNS.3 = proxy.local
IP.1  = 192.168.100.20
IP.2  = 10.10.10.10
```

Notice the typed prefixes:
- `DNS:` for domain names and wildcards.
- `IP:` for raw IP addresses.

> [!important] Production Dilemma: Mirroring CN vs. Pure SAN
> When designing an enterprise CSR and CA profile:
> 1. **Pure SAN (Modern 2026 Standard)**: Omit `commonName` entirely from the CSR. The identity lives solely in `[ alt_names ]`.
> 2. **Transitional / Backward-Compatible**: Set `commonName` to the primary domain (`labapp.com`), ensuring it is an exact duplicate of `DNS.1` in the SAN block. This avoids issues with legacy non-browser TLS clients (e.g., embedded hardware, older Java runtimes, or legacy syslog daemons) while remaining strictly compliant with CAB Forum Baseline Requirements.

## 5 · Inspecting Certificates with OpenSSL

When troubleshooting certificates on Linux, these two OpenSSL commands inspect every field:

```bash
# Inspect a local certificate file in human-readable text:
openssl x509 -in cert.pem -text -noout

# Inspect the live certificate presented by a remote server over TLS:
openssl s_client -connect 192.168.100.20:443 -servername labapp.com </dev/null | openssl x509 -text -noout
```

Key fields to check in the output:
1. `Validity -> Not After`: Has the certificate expired?
2. `X509v3 Basic Constraints`: Is `CA:FALSE` for a web server?
3. `X509v3 Subject Alternative Name`: Does it contain `DNS:labapp.com` and `IP:192.168.100.20`?
4. `X509v3 Extended Key Usage`: Does it list `TLS Web Server Authentication`?
